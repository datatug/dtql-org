Open specification · plain YAML

Queries you can read, diff, and trust.

DTQL is a portable, human-readable query language serialized as plain YAML. It is a 1:1, lossless representation of a structured query — no bespoke grammar, no hand-written parser. Save a query, hand-edit it, diff it in version control, and reload it without loss.

query.dtql.yaml YAML 
from:
  name: users
columns:
  - field: name
  - field: age
    as: years
where:
  and:
    - op: '>='
      left: { field: age }
      right: { value: 18 }
    - or:
        - op: In
          left: { field: status }
          right: { values: [active, pending] }
        - op: ==
          left: { field: country }
          right: { value: US }
orderBy:
  - field: name
  - field: age
    desc: true
limit: 10
offset: 20
01 — Why DTQL

A query is data. Treat it like data.

DTQL turns a query into a plain document you can store, review, and version — portable across every backend it runs on.

Human-readable

Plain YAML, not an opaque blob. A query reads like a small config file — anyone can open it, understand it, and edit it by hand.

Lossless round-trip

deserialize(serialize(q)) reconstructs a query structurally equal to q. Nothing is silently dropped or approximated.

Schema-validated

Published as a JSON Schema (draft 2020-12). Any tool, in any language, can validate a .dtql.yaml file before it ever runs.

Diff-friendly

Serialization is canonical — stable key order, fixed indentation. Saved queries diff cleanly in Git and review like any other source file.

Portable by design

DTQL exposes only functionality that is portable across backends, so one query runs unchanged on Git, SQLite, PostgreSQL or Firestore.

Not full SQL

A deliberately small, well-defined subset. Anything out of scope is rejected with a descriptive error rather than translated into something it isn't.

02 — Example

A query as DTQL

Columns with an alias, a nested And/Or filter with an inline In array, ordering, and paging — all in one readable file.

The document on the right selects name and age (aliased to years) from users, keeps adults who are either in an allowed status set or based in the US, orders the result, and pages it.

Every node maps to a fixed YAML shape — there is exactly one way to write it, and exactly one way to read it back.

Malformed or schema-invalid input returns a descriptive error and no partially-populated query.

03 — node → YAML

Mapping

Each in-scope query node has one defined YAML representation.

Query nodeYAML representation
From over a root collectionfrom: { name, alias? }
Columnitem under columns: — an expression plus optional as:
Comparison{ op, left, right }
Group condition (And){ and: [ … ] }
Group condition (Or){ or: [ … ] }
Order expressionitem under orderBy: — an expression plus optional desc: true
Field reference{ field: <name> }
Constant{ value: <scalar> }
Array{ values: [ <scalar>, … ] }
Operator==, In, >, >=, <, <=
Limit / Offsetlimit: <int> / offset: <int>

An expression sets exactly one of field, value or values, which discriminates a field reference, a constant, or an array.

04 — covered subset

What DTQL represents

A single source collection, the selected columns, a filter tree, ordering, and paging. Anything out of scope is rejected — never silently dropped.

In scope

A root collection source · selected columns · comparison and And/Or group trees · ordering · limit / offset. Expressions: field reference, constant, array (inline values). Operators: ==, In, >, >=, <, <=, And, Or.

Out of scope (rejected)

Joins · collection-group or parented sources · group-by · aggregate / scalar functions · cursors · any operator outside the in-scope set. Serialization errors out — it never emits a document that loses query semantics.

Lossless & canonical

deserialize(serialize(q)) is structurally equal to q; serialization is canonical, so serialize(deserialize(d)) is byte-identical to d and saved queries diff cleanly.

05 — where it runs

One query, many backends

DTQL is the portable query surface. It maps onto a data abstraction layer that adapts it to whatever storage sits underneath.

Because DTQL only expresses the portable subset, a query written once behaves the same whether it resolves against a Git repository, an embedded SQLite file, a PostgreSQL cluster, or Firestore.
